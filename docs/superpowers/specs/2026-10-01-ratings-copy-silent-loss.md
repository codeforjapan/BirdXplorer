# ratings 取り込みで COPY が無言で失われる不具合

**調査日**: 2026-10-01
**対象**: `etl/src/birdxplorer_etl/extract_ecs.py` の ratings 取り込み（ECS 日次 extract）
**状態**: 原因特定済み・未修正

## 症状

`notes` テーブルの評価集計カラム（`rate_count` / `helpful_count` /
`somewhat_helpful_count` / `not_helpful_count`）が、約 58.8 万ノートで
実データと乖離したまま固定されている。

dev（＝実質本番）の 2026-10-01 時点の実測:

```
rate_count > 0 のノート            2,904,890
うち row_note_ratings に1行も無い    約 588,000（20.25%、BERNOULLI 2% サンプル推定）
```

## 原因

`_process_rating_rows`（`etl/src/birdxplorer_etl/extract_ecs.py:857`）が、
生の DBAPI コネクションを**ループの外で1回だけ**取得している。

```python
dbapi_conn = postgresql.connection().connection.dbapi_connection   # 1回だけ

for index, row in enumerate(reader):
    ...
    if row_count >= BATCH_SIZE:          # BATCH_SIZE = 50000
        with dbapi_conn.cursor() as cur:
            cur.copy_expert(f"COPY {_STAGING_TABLE} ...", buffer)
        postgresql.commit()              # Session がコネクションをプールへ返す
```

`Session.commit()` はトランザクション終了時にコネクションをプールへ返却し、
プールは返却時に `rollback()` でリセットする。2バッチ目以降の `copy_expert` は、
もう Session のトランザクションに紐づいていないコネクションに対して実行される。
次の `postgresql.commit()` が同じ物理コネクションを引き当てれば結果的に commit
されるが、別のコネクションになれば書き込みはリセットで破棄される。

ECS の extract は `init_postgresql(use_pool=True)`
（`etl/src/birdxplorer_etl/run_extract.py:9`）で QueuePool（`pool_size=5`,
`max_overflow=10`, `pool_recycle=3600`）を使うため、どのコネクションが
返ってくるかは実行時の状態に依存する。**結果として欠損は非決定的**で、
日によって落ちるシャードが変わる。

行数カウンタ `total_rows` は Python のローカル変数なので、**破棄された行も
数え続けてログに出す**。そのためログ上は成功に見える。

## 証拠

### 1. 欠損範囲がシャード境界と完全に一致する

ratings の元ファイルは `noteId` 昇順で連続レンジに分割されている（実測）。

| file | 先頭 noteId | 概ねの作成時期 |
|---|---|---|
| 00000 | 1352796878438424576 | 2021-01〜 |
| 00001 | 1743312472432582939 | 2024-01〜 |
| 00002 | 1796486933087928816 | 2024-05末〜 |
| 00003 | 1833192482638598516 | 2024-09〜 |
| 00005 | 1911793721206616531 | 2025-04〜 |
| 00006 | 1970972125801615500 | 2025-09下旬〜 |
| 00007 | 2021318345497469065 | 2026-02〜 |
| 00008 | 2078349661245464955 | 2026-07〜 |

ノート作成年月別の stale 率（BERNOULLI 0.3% サンプル、8,785件）は、
2024-06〜2024-09 と 2025-09〜2026-02 の2ブロックだけが 100% で、
それ以外はほぼ 0%。この2ブロックは `ratings-00002` と `ratings-00006`
のレンジと厳密に一致する。

### 2. live テーブルに残っているのは各1バッチ分だけ

```
 file_no |     range_start     | live_rows_capped（100万で打ち切り）
       0 | 1352796878438424576 |          1000000
       1 | 1743312472432582939 |          1000000
       2 | 1796486933087928816 |            50000   ← BATCH_SIZE と一致
       3 | 1833192482638598516 |          1000000
       5 | 1911793721206616531 |          1000000
       6 | 1970972125801615500 |            50000   ← 同上
       7 | 2021318345497469065 |          1000000
       8 | 2078349661245464955 |          1000000
```

`50000` は `_process_rating_rows` の `BATCH_SIZE` そのもの。
**最初の1バッチだけが生き残り、以降の COPY が全て失われている。**

### 3. 行数が合う

```
ログ上の総ロード         217,386,771   （2026-09-29 の run）
file 2 + file 6 の寄与   -52,227,170
最初の1バッチ × 2本         +100,000
                        ─────────────
                         165,259,601
live の reltuples        165,262,064   （ANALYZE 推定の誤差内）
```

### 4. 元データは健全

`ratings-00002.zip` を全走査した結果:

```
rows total : 29,225,657
noteId 範囲: 1796486933087928816 〜 1833192482638598516
対象ノートの出現数 = DB の rate_count と完全一致
  1802249653506699608  3144    1812621184066077154  3444
  1810456867031966158  2309    1816548674035712393  2532
  1816977777096380690  2211    1824432322424217741  2466
  1825141482010894627  2798
```

同じノートの live 行数は 0。`rate_count` が元データと一致するのは、
過去のある時点では確かに取り込めていたことを示す。

### 5. 別経路は否定済み

- **シャードのダウンロード漏れ**: 正常な run では `00000`〜`00008` 全て
  `Successfully processed`、`00009` の 404 で正常停止。欠番ゼロ（直近14日）。
- **NOT NULL 検査での落選**: `created_at_millis` / `version` /
  `rated_on_tweet_id` が空の行は、走査した4シャード全てで **0 行**。
- **上流のデータ欠落**: 上記 4 のとおり元データには存在する。

## 併せて判明した別の問題

### A. 検証で捨てた行が計上されていない

元データ行数と取り込みログの差（＝`_validate_rating_row` が捨てた行）:

| file | 元データ | 取り込みログ | 差 | 差% |
|---|---|---|---|---|
| 00000 | 29,053,965 | 25,356,233 | −3,697,732 | −12.7% |
| 00002 | 29,225,657 | 25,921,973 | −3,303,684 | −11.3% |
| 00003 | 29,205,539 | 26,535,392 | −2,670,147 | −9.1% |
| 00006 | 27,038,594 | 26,305,197 | −733,397 | −2.7% |

落選は全シャードで常時発生しており、stale とは相関しない
（stale な file 6 が最小、正常な file 0 が最大）。`row_notes` に無いノートの
評価と見るのが自然だが、**件数がどこにも記録されていない**ため、
正常な落選なのか異常なのかを誰も判断できない。

### B. 50% ガードが機能しない

`min_rows` は live テーブルの `reltuples` の 50%
（`etl/src/birdxplorer_etl/extract_ecs.py:1014`）。今回の 24% 欠損は
76% 残るため素通しする。さらに**基準値が欠損後の live から取られる**ため、
欠損が起きるたびに閾値が下がるラチェットになっている
（217M → 165M になった結果、現在の閾値は 82M）。

## 要件

1. バッチ分割した COPY の書き込みが失われないこと。Session がコミットする
   コネクション上で COPY が実行されることを、構造として保証する。
2. staging に実際に入った行数と、取り込み側が数えた行数が一致しない場合、
   swap を中止して異常終了すること。50% ガードは残すが、これとは別に
   厳密一致の検証を置く。
3. 検証で落とした行数を、理由別にログへ出すこと。CloudWatch の
   メトリクスフィルタで拾える固定トークンを含める。

## 範囲外（別件）

- `recalculate_rating_counts` が `row_note_ratings` に行が無いノートを
  更新しない件（古い集計値が残る）。本修正で ratings が揃えば大半は解消するが、
  評価が実際にゼロになったノートの集計値は残り続ける。
- `recalculate_rating_counts` の差分ゲート化（毎日 231万行の無駄 UPDATE）。
- notes / noteStatus のダウンロードループにある「404 以外は黙ってスキップ」
  （`extract_ecs.py:354`, `417`, `940`, `952`, `967`）。今回の原因ではないが
  同種の無言障害。
